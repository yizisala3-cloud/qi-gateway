## 1. 功能理解与审查范围

用户预期是：正常静默按10、20、40、60分钟降频，主人新消息清静默；真实调用失败按5、15、60、120分钟退避，第5次及鉴权失败停用；429尊重更长Retry-After。等待从调用结束计算，并继续满足原安静期、冷却和资格条件。持久故障不能被消息、开关、跨天或重启解除，只由配置页恢复，且不自动启用主动消息、不清当天额度、不强制发送。主动评估故障不应中断普通QQ私聊。

审查以待审查目录的source-before为本地增量基线，检查策略、运行器、SQLite状态及投递回执、模型HTTP边界、设置API、前端恢复及日志归类，并沿未改动的租约与OneBot写锁路径追踪。开始时manifest的24份文件全部与当前工作树SHA256相符，见[哈希证据](reviewed-hashes.json)。本轮没有新增数据库迁移；日志module字段为text，新增qqbot分类不要求枚举迁移。

## 2. 实际执行链

- 主人私聊 → ingest/accept提交输入及revision → 取消旧主动生成 → reply_once → outbox → claim_send → 两次发送资格检查/OneBot写锁 → 回执落盘 → history及原文导出。
- 主动调度 → 在线、时段、安静期、冷却、额度检查 → begin_evaluation登记attempt/revision/租约 → 同一次模型调用判断并生成 → finish_evaluation按完成时刻结算 → 静默/退避/停用，或排队实际投递。
- 配置页 → 鉴权POST /admin/api/qqbot/proactive/resume → 设置锁 → 故障版本及租约检查 → 清故障和连续计数、保留开关及额度 → 返回状态刷新。
- 主动失败 → classify_failure → 既有日志handler及队列 → QQBot模块。采集关闭时不入队；故障状态结算与采集开关独立。

## 3. 可行动缺陷

### R13 / MEDIUM / P2：主动评估记录损坏会通过回执重试阻塞普通私聊

- 位置：gateway/qqbot_store.py:375–380（新增评估读取）；关联retry_receipts:417–424、_apply_receipt:432–435，以及gateway/qqbot.py的send_once和stop。
- 触发：已有主动消息被claim为in_flight，在等待OneBot写锁、尚未真正提交时，proactive_evaluation记录变为不可解析或校验不通过的内容。第二次发送资格检查拒绝提交，形成status=queued的本地回执。
- 根因：_send_error直接读取evaluation_state并向外抛出解析/校验异常；_apply_receipt对queued回执再次调用它，无法完成事务或清理回执。send_once先对全部回执重试，再取普通回复，所以旧主动回执会阻塞后续私聊。accept只容错了输入入库，未覆盖投递链。新输入仅作废queued主动任务，无法作废这条仍为in_flight的旧任务。
- 已复现：主人新输入被接受且reply_once生成了回复，但下一次send_once仍抛JSONDecodeError；send_receipts=1、queued reply=1、sent=[]。同一损坏记录还会使stop中的_recover抛出该异常，影响总开关切换或启动恢复。
- 影响边界：阻塞可持续到旧主动任务过期，或存储被修复。_send_error先检查expires，因此不宣称任务过期后仍必然阻塞；默认主动TTL为30分钟，可配置至2小时。
- 修复方向：对主动评估读取失败应安全拒发该主动任务并使相应回执可结算，保留损坏原记录和人工恢复要求；隔离单条主动回执错误，保证普通私聊继续投递，启动/停止不被这类校验异常卡住。
- 验收：损坏JSON及合法JSON但非法状态、写锁前后、已有queued回执重启、普通回复实际投递、开关关闭及恢复、旧主动消息不误发；正常confirmed/unknown回执与额度不重复结算。
- 证据：test_independent_recovery.py::test_corrupt_evaluation_does_not_poison_receipts_and_block_private_chat。

### R14 / MEDIUM / P2：取消已持久生效后重启，仍会误记为一次模型故障

- 位置：gateway/qqbot_store.py:192–199；对比finish_evaluation:184–185已有的revision保护。
- 触发：已有4次连续失败，第5次主动评估进行中。主人新消息已通过accept提交并更新revision、发出取消，但评估协程尚未获得下一次调度来清in_flight，此时进程异常退出。设置变化使revision失效后同样有此窗口。
- 根因：recover_evaluation只检查租约与in_flight，无条件按interrupted错误结算，没有核对attempt_revision是否早已失效。正常完成路径会将失效attempt改为cancelled，启动恢复路径却不遵守同一保护。
- 已复现：对“新输入已提交、模型刚被取消”的真实SQLite状态执行backup，结束原测试运行器后用该副本启动新运行器；failure_streak由4变5，fault_stopped=True，last_error_code=interrupted。
- 实际影响：一次由主人新消息撤销的评估触发故障停用，要求额外人工恢复；不足4次时也会错误延长退避。与图2“新消息导致取消不算调用故障”及本批迟到结果保护不一致。
- 修复方向：恢复在途评估时复用revision失效判断；已撤销请求按取消结算并保留之前失败数，真正未撤销的异常中断仍计一次故障，保持代次防护。
- 验收：新输入/设置变化后各自的中断窗口；失败数为0和4；真正第5次请求意外中断仍须停用；取消不得清除既有故障或错误恢复旧静默次数。
- 证据：test_independent_recovery.py::test_cancelled_attempt_is_not_a_fifth_failure_after_crash。

### R15 / MEDIUM / P2：同一实例租约过期后，已结束的评估可能一直保持in_flight

- 位置：gateway/qqbot_store.py:177–183；gateway/qqbot.py:149–155、471–477；前端状态与恢复入口在admin/js/pages/config.js:353–366。
- 触发：进程暂停或事件循环阻塞使30秒租约过期，模型调用完成时续租循环尚未运行；没有其它实例接管。此时内存leader仍为True。
- 根因：finish_evaluation因owns=False返回None，不清在途状态，_finish_evaluation也不进入故障/待恢复状态。之后_lease_loop成功为同一owner续租，但仅在内存leader由False变True时调用_recover_activation；previous仍为True，所以不清遗留in_flight。
- 已复现：隔离时钟前进31秒后模型正常返回；随后执行实际_lease_loop的一轮续租。数据库租约恢复、leader=True、proactive_generation=None，但evaluation_status仍为in_flight=True、fault_stopped=False、failure_streak=0。
- 实际影响：proactive_once以后始终在in_flight检查处返回，主动评估不再运行；页面却显示“AI评估中/本轮结束后计算”，恢复按钮因并非fault_stopped而禁用。需要重建运行器等额外干预，不能靠正常续租或页面恢复收敛。正常异步请求耗时超过30秒本身不会触发本项；前提是续租确实被延迟。
- 修复方向：识别实际租约中断，不能只依赖旧内存leader；在确认无本实例模型任务且拥有当前运行权后对遗留attempt进行一致的恢复。完成结算因租约失效被拒绝时，应有可重试或可人工恢复的状态；不能盲目覆盖另一实例仍在运行的请求。
- 验收：同一owner短暂失租后续租、真实另一owner接管及旧结果迟到、恢复时实际任务仍在运行、无任务遗留in_flight、状态显示和手动恢复可用性。
- 证据：test_independent_recovery.py::test_expired_lease_does_not_leave_finished_evaluation_in_flight_forever。
