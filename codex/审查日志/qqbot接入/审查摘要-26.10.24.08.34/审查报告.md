## 3. 汇总检查结果与迁移条件

### 已确认的新增代码缺陷

**0 项。** 此处结论限于把现有 NapCat 接入端迁到服务器的兼容性，不是对 QQBot 所有功能重新作无限范围审计。

活动清单中的 R11 表情摘要、R12 新账本导出命名空间仍按原状态保留，未据本轮本地测试宣布完成真实 QQ 验收。

### 条件 A：采用 Linux 安装包或容器，不能直接运行 Windows 启动入口

现有本机入口依赖 Windows 启动器和 QQNT 文件。服务器是 Ubuntu x86_64，需要独立 Linux 运行环境。

官方明确提供 Linux amd64 / arm64 Docker 部署及数据卷配置：[NapCat Docker 官方说明](https://github.com/NapNeko/NapCat-Docker/blob/main/README.md)。应选择经核对的固定版本，并为 QQ 登录数据、NapCat 配置和插件设置持久卷；不能假定 Windows 登录缓存可以无缝变成 Linux 会话，首次登录需实际验证，必要时由用户扫码。

这属于部署准备，没有发现需要为此改写网关收发代码。

### 条件 B：必须配置反向 WS，沿用当前账号和鉴权

官方 Docker 示例默认 MODE=ws，是正向 WS；网关提供的是反向 WS 接收端。直接照抄默认模式不能建立本项目所需连接。官方另有 reverse_ws 模式，ONEBOT_URL 用于指定目标；已存在的配置以 WebUI 文件为准：[官方配置说明](https://github.com/NapNeko/NapCat-Docker/blob/main/README.md#配置与更新)。

迁移时应核对：Universal 反向 WS、数组消息格式、现有 OneBot Token、原机器人账号以及证书校验。继续使用当前的 wss://yiziwanguan.com/qqbot/onebot 即可，不必改网关业务接口。部署验收时仍需确认实际请求携带 Bearer Token 和 X-Self-ID，不能仅以容器运行作为连接成功的证据。

若采用容器内网地址，localhost 只代表 NapCat 自己的容器，不能直接当作另一个网关容器。

### 条件 C：保留现有服务器账本和单连接关系

实际持久化挂载为：

- 宿主机 /data/qi-gateway/qqbot → 网关容器 /data/qqbot，读写挂载。
- 账本 /data/qqbot/messages.sqlite3 存在。
- 开关 /data/qqbot/settings.json 存在。
- 表情 manifest 存在且包含 168 项。

本次仅移动 NapCat，沿用这些目录即可。不要新建另一套网关或空 SQLite 来配合迁移；那会引入额外的数据和导出键恢复问题。

连接代码在已有 socket 时拒绝第二个客户端，不能把两个 NapCat 当作可并行接入的主备。正式切换应先确认旧专用实例停止，再由服务器实例使用原小号接入。主人的普通 QQ 客户端不属于停机范围。

### 条件 D：当前关闭状态和真实验收需要分别处理

检查时总开关关闭，因此运行器没有启动、连接状态为 false。这不是此次发现的错误，也不能靠新装 NapCat 自动解决。后续正式迁移时应在用户授权的操作范围内决定启用时间，主动消息继续按独立设置处理。

实际验收需要分别证明：容器运行、QQ 登录、OneBot 鉴权连接、主人私聊回复、图片／GIF 发送、原文导出，以及重启后恢复。
