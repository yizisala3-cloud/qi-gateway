# QQBot 接入代码审查

审查时间：2026-10-21 11:20 起，America/Los_Angeles。基线：main `635df7c` 及当前未提交的 QQBot 接入改动。

结论：**NOT READY**。确认 7 项可操作缺陷：3 项 P1/HIGH、4 项 P2/MEDIUM。建议在 QQBot 接入合并、启用前解决全部 7 项并复验。

本次只审查和复现，没有修改业务代码、部署、执行生产迁移、提交或推送。新增文件仅为本报告、测试输出和独立复现脚本。工作区原有其他前端改动不纳入本轮审查。

## 范围与预期行为

范围按用户截图的 QQBot 相关 27 文件确定，覆盖新增 QQ 模块、共享上下文和生命周期改动、配置、迁移、测试、接入文档；同时检查人格、聊天原文存储、连续感和反刍消费路径。

预期为默认关闭的单主人私聊入口，独立管理 QQ 短期会话，共用既有人格、模型及长期记忆；QQ 不调用 Eventide。输入持久化去重，连续消息合并并顺序回复；发送仅凭协议回执确认，未知结果不自动重发；主动消息遵守暂停、时段、冷却和过期规则；素材缺失与记忆不可用时应降级，不能使普通聊天失效。

执行路径：OneBot 反向 WS 鉴权及账号核验 → 主人事件 → SQLite inbox/history → 合并批次与上下文 → 模型生成 → 持久 outbox → send_private_msg/echo 回执 → confirmed 历史 → 幂等 RPC → chat_messages → 既有连续感/反刍管线。

## 确认缺陷

### R1 · P1/HIGH：当前问题被排到上一轮回复之前

- 位置：`gateway/qqbot_store.py:147-154`，`gateway/qqbot.py:157-164`，`gateway/qqbot_model.py:29,48-49`。
- 触发：生成 A 的回复期间收到 B；A 的回执先于 B 的下一轮生成到达。这是模型响应较慢时的正常连续聊天路径。
- 实际结果：第二次模型输入为 `user A → user B → assistant A`。B 虽然被用于召回 query，但 `QQModel.generate` 没有把 query 单独作为当前问题附到模型消息末尾。
- 影响：上一轮答案在请求中看起来已经回答了 B，新回复缺乏可靠的当前轮边界，可能漏答 B、继续上一段回答，或遇到上游对末尾 assistant 的限制。此处已验证请求顺序错误；未调用真实模型，未声称某家上游必然拒绝该请求。
- 根因：history 按入库 ID 排序，确认后的 assistant 总是晚于生成期间收到的新 user；`batch_history` 又无条件包含这些后来的 assistant，而不按回复所属批次组装会话。
- 修复方向：保存回复和输入批次的关联，构造“已完成历史 + 本批全部当前输入”的模型请求；保留真实到达顺序作为账本事实，另明确模型请求的当前轮边界，不能简单重复用户消息来绕过。
- 复现：`review_probes.py::RuntimeReviewProbes::test_current_question_must_remain_after_previous_answer`。实测第二轮 history 最后一项为 assistant，断言失败。

### R2 · P1/HIGH：远端记忆同步阻塞新私聊的处理

- 位置：`gateway/qqbot.py:257-275`。
- 触发：已存在待导出原文，Supabase RPC 变慢或不可用；此时主人发来新消息。
- 实际结果：`_loop` 顺序等待 `export_once`，后者逐条等待最多 20 个同步 RPC 的线程结果，期间不会再调用 `reply_once`。`to_thread` 使事件循环可以收消息，但没有释放负责生成回复的业务循环。
- 影响：主人输入会成功落盘，但远端记忆同步完成前没有新回复。慢请求和多条积压会累加等待时间，违背“记忆服务不可用时普通私聊仍可依赖本地历史”的降级要求。
- 根因：交互处理与远端导出共用一个串行工作循环。
- 修复方向：导出使用独立后台任务、受限批次和明确超时/退避；普通回复生成不能等待导出。继续保留持久导出进度和幂等键。
- 复现：`review_probes.py::RuntimeReviewProbes::test_slow_memory_export_must_not_block_new_private_reply`。阻塞模拟出口后，B 已被接受，模型调用次数仍停留在 A 的 1 次。

### R3 · P1/HIGH：缺失一张表情素材导致整个网关启动失败

- 位置：`gateway/qqbot_stickers.py:41-45`，调用链 `gateway/qqbot.py:42` → `gateway/main.py:542-545`。
- 触发：启用 QQ 且配置了合法表情目录，但其中一张图片被删除、卷中尚未复制该文件或文件不可读。
- 实际结果：构造 `StickerCatalog` 时逐项 `_read`，`resolve(strict=True)` 抛出的 FileNotFoundError 没有被降级处理，异常从 `QQRuntime` 一直传播到 Starlette lifespan。
- 影响：QQ 纯文字聊天不能启动，既有手机聊天服务也随整个应用启动失败。运行期 `_segments` 对 OSError 的处理无法保护初始化阶段。
- 根因：可选素材的单项加载错误被作为全应用初始化错误。
- 修复方向：对缺失/不可读单项记录错误并排除出可选目录，保留文字服务；目录路径越界等配置安全错误仍可明确拒绝，但应避免无关功能被可选资源拖停。
- 复现：`review_probes.py::CatalogReviewProbes::test_missing_optional_sticker_must_allow_text_runtime`。仅缺少 `missing.gif` 即在运行器构造阶段抛出 FileNotFoundError。

### R4 · P2/MEDIUM：临时入队失败会永久遗留 working 输入

- 位置：`gateway/qqbot.py:157-160,174-175`，`gateway/qqbot_store.py:133-139`。
- 触发：`batch()` 已提交 pending → working 后，读取本批历史或将生成结果入 outbox 时遇到可恢复的本地数据库错误。
- 实际结果：外层循环只记录异常；本批仍是 working。`batch()` 后续仅选择 pending，因此数据库恢复后也不会重试本批。
- 影响：该条输入持续没有回复；重放又被去重。`pending()` 把 working 也算作待处理，主动消息也会持续被拦截，通常需重启触发 recover 才恢复。
- 根因：批次认领独立提交后，失败路径没有释放或恢复批次；recover 仅发生在启动/领导权变化/停止阶段。
- 修复方向：为工作批次增加可恢复的认领和失败状态；失败时核对 outbox 是否已提交，再安全重试本地入队或恢复输入资格，不能重复网络投递。
- 复现：`review_probes.py::RuntimeReviewProbes::test_transient_outbox_error_must_not_strand_inbox`。用 SQLite 临时写入失败触发器中止入队、移除触发器并再次处理后，inbox 仍为 `[(1, 'working')]`，outbox 为空。

### R5 · P2/MEDIUM：单条导出失败后继续后续行会颠倒远端对话

- 位置：`gateway/qqbot.py:258-265`，`gateway/qqbot_store.py:222-228`。
- 触发：同一轮 user 原文的 RPC 首次失败，紧随其后的 confirmed assistant 导出成功，稍后 user 重试成功。
- 实际结果：远端插入顺序成为 `assistant → user`；已保存正确的 created_at 不能修复这一点，因为连续感读取使用 `.gt('id', cursor).order('id')`，反刍也按 ID 排序处理。
- 影响：机器人答案变成孤立发言，可能与后续不相干输入组成错误轮次；如果摘要游标已推进，后到的 user 也不能和原答案一起消费。
- 根因：导出逐行独立失败重试，前面的失败项不会阻止后面的同会话记录被提交。
- 修复方向：同一会话按持久导出游标顺序提交，遇失败停止该会话后续导出；或通过事务批量 RPC 保存有序消息，继续保留逐条幂等性。
- 复现：`review_probes.py::RuntimeReviewProbes::test_memory_export_must_preserve_conversation_order_on_retry`。仅注入一次 user 导出失败，实测出口接收顺序为 `['assistant', 'user']`。

### R6 · P2/MEDIUM：连接核验期间到达的主人消息被静默丢弃

- 位置：`gateway/qqbot_transport.py:127-128`，核验状态设置于第 75-78 行。
- 触发：反向 Universal WS 已接受且 Token/X-Self-ID 正确，在 get_login_info/get_status 完成前收到合法主人私聊。新连接和重连期间均存在该窗口。
- 实际结果：接收循环读取事件，但 verified 为 false 时既不交给 ingest，也不保存/暂存；核验结束后不会重新处理。
- 影响：这条消息没有本地原文、没有任务、没有回复。当前实现也没有历史补取过程，不能依赖协议端一定重放来补救。
- 根因：将“未完成账号核验”直接实现为丢弃接收事件，而非等待核验后再交付。
- 修复方向：在账号核验阶段有界暂存已鉴权连接上的事件；确认真实账号后按顺序重新校验和交给持久入口，核验失败则全部丢弃。
- 复现：`review_probes.py::TransportReviewProbes::test_owner_event_during_identification_must_not_be_lost`。连接最终 verified=true，但核验期间那条主人事件的回调次数为 0。
- 协议依据：[OneBot 反向 WebSocket 文档](https://github.com/botuniverse/onebot-11/blob/master/communication/ws-reverse.md)描述 Universal 连接同时提供 API 和事件服务；没有本实现的额外业务核验完成屏障。因此不能假设推送会等 get_status 回执。

### R7 · P2/MEDIUM：发送超时没有覆盖 socket 写入

- 位置：`gateway/qqbot_transport.py:43-47`。
- 触发：大图/多图发送时协议端读取缓慢，或连接存在半断开/背压，导致 send_json 等待。当前素材上限允许单张 8MiB，多张可累计到更大的 WS 帧。
- 实际结果：action_timeout 仅在 send_json 返回之后才包住回执 future；等待 write_lock 和 send_json 本身均没有超时。
- 影响：send_once 和 send_lock 可长期挂住，outbox 留在 in_flight，后续所有文字和表情也无法投递；配置的发送超时不能解除该状态。
- 根因：超时只覆盖回执阶段，没有覆盖完整动作生命周期。
- 修复方向：让超时覆盖排队、写入和等待回执；已开始写入后超时应保守记 unknown，不自动重发。仅能证明尚未提交时才允许 queued 重试。
- 复现：`review_probes.py::TransportReviewProbes::test_action_timeout_must_bound_socket_write`。使用合法配置 action_timeout=1，模拟阻塞 send_json；1.2 秒后发送任务仍未结束。
