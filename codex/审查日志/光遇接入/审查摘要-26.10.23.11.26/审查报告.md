## 功能、范围与证据

实际链路：MuMu 截图 → 本地 OCR → 具名玩家与新消息判断 → Inbox 连续收件 → JSON 玩家身份及主要用户优先提示 → 模型 PASS 或短回复 → 原生草稿/输入/回显确认 → 交付接口 → 原子、幂等保存 → 下一批。

主要用户权重通过 system 提示词及“本轮是否包含主要用户”提示实现。完整 PASS 才表示静默，不输入、不发送、不进入本地 assistant 历史；确认当前批次时保留后来入队的消息。没有将“没有硬编码回复率”作为缺陷。

范围包含桥接、OCR、配置、依赖、启停脚本、私人发布脚本、gateway/main.py、sky_delivery.py、相关上下文/持久化模块、新迁移和测试；未混入无关前端、规划及 QQ 改动。发布脚本只静态检查，未执行 SSH、构建、发布、重启或回滚。

## BUG-06 · MEDIUM / P2 · 名字被误切，主要用户优先权给错人

- 位置：tools/sky_companion/bridge.py:272–284，影响 707–714。
- 条件：OCR 识别的名字含 -、·、—，如“叶·子”“阿祁·叶子”。
- 实际结果：贪婪正则从最后一个分隔符拆分。“在吗 - 叶·子”得到 sender=子、text=在吗 - 叶；“你好 - 阿祁·叶子”得到 sender=叶子。
- 影响：前者丢失主要用户身份，后者将其他玩家提升为主要用户，并实际追加“本轮确实包含主要用户发言，应优先回应”的系统提示，影响回复权重和关系判断。
- 证据：独立回归前 5 项失败，含三种分隔符、误认他人及 chat_messages → conversation_query → Gateway.generate 链路；无需模型误判即可触发。
- 修复方向：依据实际发送者标签或行布局确定完整名字，区分消息边界与名字内部标点；无法确定时不能将名字末段提升为主要用户。
- 验收：含符号名字完整保留，正文含分隔符也不截错，他人名字以主要用户名结尾不获得其优先权。

## BUG-04 · MEDIUM / P2 · 同位置新回显仍被判为发送失败

- 位置：tools/sky_companion/bridge.py:217–227、851。
- 条件：旧“好的”已在画面下方，群聊滚动使其离屏，新发的“好的”又位于相同位置。
- 实际结果：同文数量都是 1，bottom 相同，两项判据均不成立。其他行已显示整个序列换新，函数仍返回 False。
- 影响：发送成功、草稿清空后仍报未确认，主循环退出，不能走后续交付确认。
- 证据：独立回归最后一项，原、新同文均 y=740，其他 15 条新群聊替换旧序列，仍不确认。简单的上方旧消息/下方新消息场景现在已通过。
- 修复方向：结合完整可见序列的滚动变化识别新增消息，不能只比较匹配文字的数量和末尾位置；保留不确定时停止且不重发的约束。
- 验收：同位置替换、旧同文消失、普通滚动、换行/气泡变化均覆盖；旧回显或他人引用不能假报成功。

## BUG-07 · MEDIUM / P2 · 收件批次超过生成长度上限，整轮退出

- 位置：tools/sky_companion/bridge.py:365–386、673–674、905–908。
- 条件：积压数量未到 Inbox 的 1000 条上限，合并 JSON 已超过 20000 字符。
- 实际结果：take() 一次拿走全部 pending，generate() 随即拒绝，异常退出循环；重启按既定设计不会自动重放旧队列。
- 影响：该批主要用户消息一并无法处理，需要人工恢复。这是两个模块的批次边界不一致。
- 证据：400 条短消息加 1 条叶子问句可入队，合并为 24777 字符。该用例验证积压边界，未声称当前现场已达到此流量。
- 修复方向：按实际序列化字符预算取批，保留剩余与后来入队消息；单条超限单独处理，不能终止整个有效队列。
- 验收：低于条数上限的超字符积压可分批完成，临界值不越限，PASS/确认只处理当前批次，不漏不重。

## BUG-08 · MEDIUM / P2 · 身份自动发现变化后，相同交付补交持续冲突

- 位置：gateway/sky_delivery.py:40–45；迁移 SQL 37–43；bridge.py:664–668、898。
- 前提：未固定 MEMORY_ASSISTANT_ID，或恢复前配置改变。首次交付已入库但回执丢失，随后其他客户端写入不同助手身份，使自动发现结果变化。
- 实际结果：相同 delivery_id/query/text/confirmed_at 重交，服务端却重新解析助手身份，而该身份参与载荷哈希。同一交付返回 409，文件一直未确认，启动补交每次都中止。
- 影响：第一次记录可能已经完整，本机仍无法自行恢复。固定身份不变时不触发；本轮没有观察到生产身份已经变化，不描述为每次重启必现。
- 证据：独立回归模拟前后发现结果不同，原样交付产生 delivery_payload_conflict；只读 SQL 也验证实际哈希不同，生产函数体与本地来源一致。未向生产发送试验交付。
- 修复方向：冻结首次交付的身份上下文，或用既有交付的原身份校验不变的客户端内容，不能依赖最新助手身份重建同一交付。
- 验收：丢回执后身份变化仍得到原消息对，真实正文变化仍冲突；不改写原助手归属、不重复插入。
