# 控制台延迟优化代码审查

结论：**NOT READY**。确认 3 个 P2 缺陷，均有独立执行的失败断言。

审查对象为 `main`（HEAD `c885f3b`）工作区内的本批延迟优化。用 `../控制台延迟优化-20261025/before/` 快照区分优化增量与工作区原有改动，覆盖新命令及迁移、规划回执和后台校准、配置分片、记忆分页、总结与日志并行读取、入口依赖调整。截图中的 9 个文件并非完整改动范围。

## CL-01：实例回执被误当成任务，覆盖另一条任务缓存（P2）

位置：`admin/js/pages/planning.js:562–564`。

`serialize_occurrence()` 返回的实例也包含 `task_type`。`applyCommittedReceipt()` 用该字段判断顶层结果是任务，再以 `result.id` 匹配任务 ID；这个 ID 实际上是实例 ID。

独立复现中，任务 3 的实例 8 执行开始后，任务 8 被替换为该实例对象。它的正文变成任务 3 的实例正文，并丢失 `is_active`、`refresh_enabled` 等任务字段。全部待办会据此误显示“已删除”，详情动作和规则也会异常；只有后台任务列表刷新成功后才恢复。

建议：明确区分任务回执与实例回执，实例对象只能按实例 ID 合并，不能写入任务缓存。

证据：[前端探针](receipt_repros.mjs) 第一项；[失败输出](frontend-repros.txt)。

## CL-02：回执重绘会清空正在输入的计时器草稿（P2）

位置：`admin/js/pages/planning.js:573–575`。

命令请求尚未返回时，用户仍可在当前详情的计时器框中输入。成功回执调用 `showOccurrenceDetail(row)`，没有启用现有的 `preserveInputs` 分支，直接重建整个详情。`detailEdit.isActive()` 不覆盖尚未触发保存的普通计时器输入。

独立复现中，正在聚焦的计时器输入值为 `17`，开始回执到达后变为空字符串，原输入节点也被替换。原有列表校准使用 `preserveInputs: true`，本次新增的立即回执路径绕过了这项保护。

建议：回执更新详情时沿用保留输入的更新方式，并覆盖请求等待期间继续输入的场景。

证据：[前端探针](receipt_repros.mjs) 第二项；[失败输出](frontend-repros.txt)。

## CL-03：物理删除任务后，新回执表仍保留完整正文和备注（P2）

位置：`supabase/migrations/20261025010000_planning_occurrence_commands.sql:143–145`。

每次开始／部分完成／完成会把完整任务和实例行存入 `planning_occurrence_command_request.result`。现有物理删除事务没有清理此表，也没有外键或其他清理机制。

在隔离 PostgreSQL 中创建含正文和备注的任务，只执行开始，再走真实删除事务：返回 `history_preserved=false`，任务及实例均为 0 行，但新回执表仍能读取原正文和备注。这违反既有“无完成事实时物理删除相关业务内容”的语义；原创建身份删除登记特意只保存摘要，新增回执重新留下了完整副本。

建议：让物理删除事务同步清理或脱敏这些回执，并用最小删除身份表达后续幂等重放，避免继续保留正文。

证据：[真库探针](deletion_repro.py)；[失败输出](deletion-repro.txt)。只使用一次性本地 PostgreSQL，未连接生产数据库。
