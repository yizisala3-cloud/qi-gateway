## 工作区与文档管理规则

1. `codex/控制台-文档索引/目录说明.md` 是工作区目录分类和文档维护规则的唯一入口；`控制台-文档索引`文件夹内只保存本说明，不得在其中新建任何子文件夹或其他文件——代码修改日志、审查日志、规范、需求等一律放 `codex/` 下的对应平级文件夹。
2. 目录名称、用途或维护标准发生变化时，直接更新本说明。
3. 文档按用途放入对应目录；未确认信息标记“待确认”，计划、当前状态、长期维护和代码修改记录分开保存。
4. `网关当前状态` 只保留一份统一文本，不再拆分前端、后端文件。
5. 纯目录整理、文档移动、规范编辑、需求文档维护和审查归档不属于代码修改，不得写入“代码修改日志”。
6. 执行 Debug / Bug 修复任务时，用户未明确指定规范版本，默认遵循[debug规范-简洁版](../操作规范/debug规范-简洁版/debug-protocol.md)；用户明确要求普通版或对应加强版时，按指定版本执行。

## 合并前检查与数据库迁移规则

生效与授权：用户2026-10-13明确要求，后续合并前检查必须落实迁移，短迁移由AI自行执行，较长迁移可以提供文件地址供用户复制粘贴。详细流程统一维护在[合并前检查规范 §5](../操作规范/合并前检查规范/pre-merge-check-protocol.md)，审查和Debug规范引用该入口。

1. **合并前逐份核对。** 检查完整候选和运行依赖，包括更早提交或另一工作区引入的迁移；不能因本轮只有前端变化就忽略已有后端所需SQL。核对当前状态、目标项目及实际表/列/约束/触发器/RPC/权限和执行记录；Git里有SQL、本地真库测试通过不表示生产已执行。
2. **短迁移直接执行。** 本次选入改动所需、目标和依赖明确且尚未执行的短SQL，由AI按兼容顺序自行运行并核验，不再仅因属于生产数据库或保存为.sql文件重复询问。当前任务明确“只审查”“不操作生产”或指定延期的限制优先；不借此执行无关历史或用户暂缓的迁移。
3. **长迁移可以交接文件。** 根据完整SQL篇幅及工具执行能力判断，不设未经用户确认的固定行数。交接时给可点击的完整绝对文件地址、目标项目/环境、前置条件和多文件执行顺序，供用户在SQL Editor完整复制粘贴；等待实际执行结果，再核验数据库对象和所需缓存，不把“已给地址”当作执行完成，不截断或拆分脚本绕过交接。
4. **状态和证据逐项保留。** 报告列明迁移文件及来源版本、目标、依赖/顺序、实际对象证据、执行与核验状态、执行者及下一步。缺迁移、执行失败或未核验的运行前置条件必须在结论中突出；不得只在推送成功后附一句提醒，也不得用延期其它Bug代替数据库前置条件已满足。
5. **区分四种结果。** 代码已推送、数据库迁移已执行并核验、服务部署已确认、线上业务已验收分别记录。需要的迁移未落实时不能无条件宣布READY或功能已可用；自动部署涉及新数据库对象时，先落实兼容的发布顺序。当前状态与本索引同步实际结果，历史审查和修改日志不改写。

## 代码修改日志规则

1. 只有实际修改源代码、数据库迁移、测试代码或与功能实现直接相关的配置与资源时，才登记“代码修改日志”。
2. 目录结构统一为工作区内 `codex/代码修改日志/对应实际功能/修改正文.md`；不存在对应实际功能目录时再新建。
3. 每次代码修改单独建立一个 Markdown 文本，不得把不同修改持续追加到同一文本；跨功能修改放入主要功能目录，并在正文列明范围。
4. 文件名和一级标题使用“本次代码修改的简要总结-YY.M.D.HH.mm”，时间精确到分钟。
5. 正文至少写明修改时间、涉及代码范围、修改原因、修改内容、验证结果和遗留事项。
6. 时间戳使用执行代码修改时的本地时间；无法可靠取得时先询问用户，不得猜测。
7. `代码修改日志/旧版修改日志` 是只读历史归档区，按前端、后端分开保存，不适用新增日志结构。

## 功能维护规范规则

1. “功能”只指实际产品功能或代码功能，例如规划管理、记忆管理等用户可使用或代码直接实现的业务能力。
2. 工作区、需求、目录、日志和其他文档管理分类不属于“功能”，不得放入“功能维护规范”。
3. 目录结构统一为“功能维护规范/对应实际功能/对应实际功能.md”。每个实际功能目录只保留一份同名 Markdown 文本。
4. 已有对应功能目录时直接更新原规范；没有时才新建功能目录及其唯一规范文本。
5. 规范文本记录该功能的长期维护约定、稳定约束、关键依赖或接口、维护方法、验证要求、已知风险和后续注意事项。
6. 短期实现进度写入“网关当前状态”；代码修改过程与结果写入“代码修改日志”，不得重复堆入功能维护规范。

## 需求维护规则

1. `需求` 统一存放经用户明确确认的业务需求及各功能的待修复缺陷。业务需求按不同批次分别维护，同一批次补充和修订更新原文档；技术缺陷按功能集中维护在后续待修复文档。
2. 当用户明确说明“这是一个新需求”，或以同等清晰方式确认形成新的业务需求批次时，才新增正式业务需求文档；审查确认的缺陷没有对应活动文档时，按下文持续授权新建后续待修复文档。
3. 未经用户明确确认的想法、推测、建议或新业务需求，禁止写入正式业务需求文档。代码审查确认的技术缺陷按下文“后续待修复文档维护规则”直接登记；未经证实的猜测不能登记为已确认 Bug。
4. 用户只表示“后续再做”时：已有对应需求可以保留并标明后续处理；没有对应文档时，只有用户同时明确确认其为需求后才能新增。
5. 修改代码时，只有与用户明确确认新的预期效果、代码方向和本次明确不做的内容后，才可以更新对应需求文档；属于现有批次则更新原文档，明确属于新需求时才新增。
6. 正式业务需求文档只记录用户确认的目标、预期效果、范围、明确不做内容、验收条件和未完成事项，不记录未经确认的技术设想、实现流水或代码修改日志；后续待修复文档记录经审查确认的缺陷、根因、证据和修复验收，不据此新增或扩大业务需求。
7. 用户明确表示“这次功能改动完成”或以同等清晰方式确认完成后，可以删除对应已完成业务需求。文档中仍有未完成内容时不得删除整份文档；后续待修复的条目按下文“全部子场景修复并验收”标准移除。
8. 未完成或用户明确表示后续再做的业务需求可以保留；不得仅凭代码合并、测试通过、部署完成或实现者判断擅自认定业务需求完成。技术缺陷是否关闭依据该条目的完整修复验收证据核对，不以普通测试全绿替代逐项验收。
9. `需求/旧版需求/前端` 和 `需求/旧版需求/后端` 只保存迁移前历史材料，不再新增，后续可按用户要求删除。
10. `需求/规划管理` 中的两份需求文档相互独立：`规划管理 · 第一期完整需求规范.md` 是当前维护文本；`规划管理-一至三期完整需求（旧版）.md` 只供查阅，后续不得更新。`规划管理 · 第一期 Implementation Plan.txt` 是实施计划，不作为需求来源；`Phase0-baseline-20260924-150833` 是本次基线快照，不作为代码修改日志。
11. `需求/备忘录/备忘录一期完整需求/需求规范.md` 是当前备忘录批次的统一需求文本。经用户 2026-10-02 指示，一期已确认改动与后续待添加改动放在同一份文档中，明确标注一期要做、一期预留、后续才做及后续仍待确认的细则；后续功能未确认进入本期前，不得作为一期实现或验收要求。
12. `需求/前端待修复/前端待修复清单.md` 经用户 2026-10-02 指示建立，是本批次前端待修复项的统一维护文本；具体位置、状态、验收与后续补充在该文档维护，长期视觉/组件规则仍维护在“操作规范/前端视觉规范”。本清单登记不代表已实施、已验证或已部署，不替代规划管理原有的业务缺陷清单。
13. `需求/备忘录/后续待修复.md` 是备忘录当前未解决问题的唯一活动清单，按下文统一规则维护。历史已发布编号不重排、不复用；同根因残留或回归更新原条目，独立新问题按该功能历史最大编号递增。`阻断问题修复Debug指令.md` 保留原 BUG-01–BUG-04 修复范围，执行前以当前活动清单及最新审查证据核对；实际修复按 Debug 规范执行，文档更新不表示代码已修或已部署。

## 后续待修复文档维护规则

生效与授权：用户 2026-10-03 明确要求。适用于所有功能的后续待修复文档，包括现有不同文件名或位于“后续待修复/”子目录内的活动清单。

1. **审查发现必须登记。** 每次代码审查确认的 Bug，必须在本次审查结束前同步更新 `需求/对应功能/` 内该功能的后续待修复文档，不能只写审查报告或只在聊天中说明。这是持续授权，不需要逐次询问是否登记；登记缺陷不等于授权修改业务代码。
2. **先找已有文档，缺失才新建。** 先查控制台索引及对应功能需求目录，优先更新该功能已有的后续待修复文档；没有对应文档时，在 `需求/对应功能/` 新建 `后续待修复.md`，必要时创建功能目录，并同步本索引。已有目录和文件名沿用，不按每次审查另建一份活动清单；同一功能有多份现存材料时，先核对其当前归属和编号，明确唯一活动入口，历史证据留在日志。
3. **更新前逐项核对旧问题。** 根据当前源码和已有修复、验收证据检查原条目，不照抄过期状态，不因修改日志写“已修复”或普通测试全绿就认定所有子场景通过。条目的全部子场景已修复并验收后，从活动清单删除；已改代码但尚未完成验收的保留为“修复后待复验”；仍有失败场景的保留为“待修复”，并更新剩余触发条件。已修结果与历史经过放对应修改/审查日志，不把已解决条目长期挂在活动清单。
4. **先比根因，再决定合并或新增。** 新发现先与该功能现有条目及已删除条目的历史记录比较，检查是否为残留、相似问题或回归。由同一原因引起的不同表现合并为同一 Bug，沿用原编号，补齐全部触发条件、影响和验收子场景；同根因问题删除后再次回归时，恢复原编号。仅仅同一文件、相似症状或同属一个功能，不足以合并；独立根因必须单独登记。
5. **新编号从历史最大值递增。** 每个功能使用统一的编号序列；独立新 Bug 沿用该功能既有前缀和格式，从该功能历史最大已发布编号加一（如 BUG-11 后为 BUG-12），不能只看仍在清单中的最大值。首次没有编号时从 BUG-01 开始。禁止填已删除编号的空缺、每轮重新从 01 编号、重排旧编号或把旧编号分配给不同根因；恢复同根因旧条目不属于分配新编号。活动文档保留“历史最大已发布编号”和“下一个新编号”，保证删完旧项后仍可继续递增。
6. **同一功能禁止重复编号。** 同一功能的活动清单、子清单和引用必须共用同一编号登记，禁止两个不同 Bug 使用相同编号，也禁止前后端或不同审查批次各起一套相同序列。多个证据或子场景可以引用同一条目的编号，不得复制成重复条目。不同功能独立编号。
7. **条目要能用于修复和验收。** 每项至少写明唯一编号、严重度、准确状态、用户会遇到的问题、触发条件、代码位置与根因、修复方向、验收条件及最新审查/复现证据链接。合并时保留未通过的全部子场景，已通过的必要场景只列作回归保护；原审查报告和原始证据不覆盖改写。
8. **完成前检查一致性。** 核对活动条目数量、表格与正文编号、同功能编号唯一性、历史最大编号及下一编号、证据链接和控制台索引状态一致。纯待修清单或维护规则更新不写入代码修改日志，也不能表述成代码已修、已验收或已部署。
